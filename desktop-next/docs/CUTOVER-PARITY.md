Corrections to the brief:
- `canvas-api.ts` does not exist. The canvas route is `S/handler-status.ts:152`, and only `canvas-api.test.ts` exists.
- `/api/runs` is the reusable-run library. The workflow-run ledger is `/api/workflow-runs` (`S/workflow-run-api.ts:8`).
- The public API is not served by the desktop app. `serveDesktop` never enables it (`S/server.ts:154-165`); it is started by `vanta api serve` (`src/cli/api-cmd.ts:12`).
- The "operator dossier" is `OperateView`, which only exists in the Classic shell (`R/operator-views.tsx:11`, reachable via `?shell=classic`, `R/chat-first-navigation.ts:9`).
- I found no feature named "telemetry-free operator profile". The closest are the telemetry removal and network audit (row V-021) and the runtime usage-telemetry line in the runtime strip (V-041).

**(4) Risks of retiring the old renderer**
- **The new app imports the old tree.** It imports `process-tree`, `project-root`, `runtime-env`, `runtime-launch`, `runtime-paths`, `project-switch`, `project-folder-picker` and `dropped-paths` from `vanta-ts/desktop-app/electron` (`NE/launcher.ts:7-14`, `entry.ts:5`, `project-handlers.ts:3-9`, `runtime-root.ts:3`). It also uses `desktop-app/build/vanta-brand-icon.svg` (`tools/make-icons.mjs:14`). Deleting `desktop-app` breaks the new app, so move these first.
- **The server serves the old bundle.** It serves `/` and `/companion` from `desktop-app/dist` (`S/assets.ts:19-26`), and the new package bundles that legacy renderer (`D/PACKAGING.md`).
- **Companion and iOS depend on the same bundle.** `R/main.tsx:32-34` and `capacitor.config.ts` (`webDir: desktop-app/dist`) both do.
- **The proof suite is coupled to the old shell.** 41 of 51 `SC/desktop-*.mjs` scripts plus `lib/*` reference the old shell, and 39 launch `desktop-app/electron/main.mjs`. There are also 80 renderer test files and 12 Electron node-tests. No equivalent proofs exist yet for continuity, workflow, look, queue, recovery or the trust packaged proofs.
- **The release path is old-app only.** `package.json` `main` is `desktop-app/electron/main.mjs`, and `desktop:release` notarizes only the old app. The new app is unsigned with no update feed.
- **Safety gaps today** (all in the table): V-018, V-019, V-022, and the extra entitlements in the new plist.
- **State does not migrate.** The old origin is `http://127.0.0.1:<port>`, so localStorage keys do not carry: selected chat (`vanta.desktop.selected-chat.v1:<root>`), sound, theme, full-access acknowledgement. userData also differs ("Vanta" vs "Vanta Next").
- **Classic-only surfaces disappear:** the queue drawer, `OperateView` and the classic sidebar.
- **Plan decision D8:** the installed `Vanta.app` is the old renderer and should not be swapped before parity.
- **New-app status:** D STATUS says the done path is met on source Electron only, with a scripted model. Wireframe parity is 2.1%.

## Update 2026-10-14: V-008 and V-006 ported (branch `claude/desktop-pw-receipts-queue-20261014`)

The V-006 and V-008 rows above describe the state before this branch; their "Desktop-next today" cells are out of date.

- **V-008 run receipt recovery**: `POST /api/chat` now returns `stoppedReason` beside the receipt. The gateway keeps the full receipt (`schemas.ts` `runReceiptSchema`) and ends a failed run from the chat response (the typed `turn.complete` for a failure is held back, because only the response carries the actions and checkpoint). Each reason has its own headline and body (repeated failure, step limit, tool-call limit, context limit, blocked; failure kinds tool, model, denied, setup, unknown), sent as `error_surface` with `partial: true` so the output the run produced stays on screen. The error card shows the three saved actions, each only if the server offered it: **Retry the step** (the card's reload), **Edit request** (the edit box on the request), **Start from checkpoint** (the checkpoint prompt goes to the message box; the user sends it). Words: `src/api/vanta/run-stop.ts`. The provider_auth card and runs the user stopped are unchanged.
- **V-006 queued-turn editor**: the composer queue is the server's durable queue. Gateway methods `queue.list`, `queue.enqueue`, `queue.action` (edit, move, cancel, steer, retry, each with the item's revision; a stale revision comes back as a result with a plain reason and the current list) and `queue.run`. The panel shows state per message (runs next, steer now, starting, not sent plus reason), move earlier/later, retry, steer, send now, remove, edit in the message box, and "Run queue" when nothing is running. `POST /api/chat {resumeQueue: true}` is new server code: after an app restart no running turn drains the queue, so the user asks.
- **Differences from the old renderer, on purpose or by limit**: (1) a saved message with attachments stays in the window's own queue (the server queue carries text only); (2) Steer on a saved message means "run next, after the running instruction", because the server never interrupts a running instruction to reach the queue; (3) a run the user stopped keeps the existing stop display and shows no failure card.
- **Gaps**: see PARKED.md (live thread does not show queued user messages until the chat is reopened; schema-trace explorer V-009 not ported; a conflict while arrow-stepping through edits loses the typed words).
- Evidence: `docs/proofs/receipts-queue/` (real Electron app, sandbox VANTA_HOME, scripted model). Re-run: `node tools/receipts-queue-proof/run.mjs --out <dir>`; repeated: `node tools/receipts-queue-proof/flake.mjs --runs N`.
