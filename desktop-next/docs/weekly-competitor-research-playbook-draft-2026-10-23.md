## Purpose

Produce a short, source-linked account of meaningful competitor changes and
their implications for the owner's product. Optimize for useful decisions,
not a long feature wishlist or repeating last week's findings.

## Inputs

- Owner-confirmed product, research question and competitor/source list.
- Last approved brief and its dated source/version inventory, if one exists.
- Existing approved templates and source-review assets from the Toolbox.
- A seven-day window ending on the run date, with timezone Europe/Madrid.
  This window is a proposed default, not an approved reporting rule.
- Read-only public sources by default; private sources require explicit scope.

## Steps

1. Confirm current authority and resolve the open input decisions before a run.
2. Check the Toolbox and prior brief first. Reuse compatible approved assets;
   do not rebuild the template or claim candidate material is approved.
3. Capture the actual source date and version/commit for each selected source.
   Separate release, documentation and implementation evidence.
4. Compare with the prior baseline. Record a new baseline explicitly on run one;
   do not invent a previous-week delta. Deduplicate prior findings.
5. Inspect primary evidence for each retained change. Distinguish observed
   source behavior, vendor claims, inference and unavailable evidence.
6. Summarize what changed, why it matters to the owner's question, and whether
   to investigate, adopt, defer or take no action. Do not implement automatically.
7. Run the Proof of Done below, fix only demonstrated report defects, then
   present the brief plus gaps and the actual asset reused.

## Decisions and edge cases

- Nothing new: report the checked source/version inventory and no material
  changes; do not manufacture recommendations.
- Source inaccessible or rate-limited: record the gap, do not imply it was read,
  bypass login/controls or silently replace it with unsupported recollection.
- Conflicting evidence: show the disagreement and downgrade the conclusion.
- Large release: prioritize changes tied to the approved question, state
  excluded areas and stop at the agreed effort limit.
- Code reuse: check the exact pinned license and notices before recommending a
  copy. A general repository license is not proof for every dependency/file.
- Missing baseline: mark the first brief as a baseline, not a weekly comparison.

## Format

Proposed Markdown brief: reporting window; decision summary; change entries
(competitor, change, primary source/date/version, evidence level, implication);
recommended next action; checked source inventory; gaps; Proof of Done.
Length, destination and delivery remain owner decisions. No outward delivery.

## Proof of Done

Before returning each actual brief, report pass/fail/unverified with evidence:

1. Product, question, source list, window, output location and limits match the
   owner's reviewed procedure; cite the approval reference.
2. Every retained factual change has a supporting primary link, inspected
   version/date and evidence level; inaccessible sources are listed as gaps.
3. Each delta is compared with the real prior baseline, or run one is labelled
   baseline; duplicates are excluded or labelled as continuing issues.
4. Recommendations connect to the approved product question and distinguish
   adoption proposals from implemented or tested functionality.
5. The brief uses the approved format, contains the checked source inventory,
   and identifies the actual reused approved asset (or honestly states none).
6. No secrets, unsupported completeness claims, unapproved account effects or
   invented owner approvals enter the output or Toolbox.
7. Open proof failures remain visible; a reviewable draft is not called a
   completed research run. A missing authority decision stops that action.

Adoption requires owner review first, then two real runs. Run two must reuse
an approved saved asset, and both must pass the actual checks. Neither run has
been executed. Proposed repairs to this procedure also require review.
